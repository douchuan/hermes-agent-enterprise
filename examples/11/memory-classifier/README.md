# 示例：Memory 敏感信息分类器

对应书籍：第 11 章 — Prompt Injection、Memory 与 Skills 的安全治理

## 目的

演示如何对 Hermes Agent 的 Memory 条目进行敏感信息分类，确保跨员工和跨租户的 Memory 不会被不当共享。

## 原理

分类器采用**确定性规则**而非 LLM，原因：

- LLM 推理成本和延迟高，分类结果不稳定、不可重复。
- 敏感内容可能需要外发到模型，增加泄露风险。
- 难以审计"为什么这样分类"。
- LLM 可能被 Memory 中的恶意指令影响。

分类规则基于：
1. **来源元数据**：对话、文档、工具结果、网页抓取、Skill 输出等。
2. **关键词规则**：匹配密码、Token、API Key、SSN 等敏感模式。
3. **部门绑定**：某些 Memory 仅对特定部门可见。
4. **保守策略**：无法分类时采取限制访问的默认行为。

分类结果（`SensitivityLevel`）与访问控制**解耦**：分类不替代授权检查。

## 运行方式

```bash
cd examples/11/memory-classifier
npm install
npm test
```

需要 Node.js 18+。测试不依赖外部服务。

## 预期结果

测试应全部通过，展示：
- 不同来源类型的 Memory 分类结果
- 关键词规则匹配（密码、Token、身份证号等）
- 部门绑定的 Memory 可见性
- 无法分类时的保守处理
- 分类结果与访问控制的解耦

## 关键设计

- **规则优先于 LLM**：第一阶段使用确定性规则，确保分类结果可重复、可审计。
- **保守默认**：`unknown` 级别的 Memory 默认限制访问，防止误分类导致的信息泄露。
- **分类与授权解耦**：分类结果仅作为参考，实际访问由 Tool Gateway 或 Control Plane 的授权模块决定。
- **可扩展规则集**：规则通过配置注入，不硬编码在分类逻辑中。

## 安全边界

- 本示例的分类规则是教学简化版本，实际需要更完善的规则集。
- 分类不替代授权检查——即使分类为 `public`，也需要验证请求者是否有权限访问该 Memory。
- 示例未实现规则的动态更新和版本管理。
- 示例中的关键词规则是基础版本，可能无法覆盖所有敏感信息模式。

## 生产差距

生产环境需要补充：

- 更完善的关键词规则库（正则表达式、NLP 模式匹配）。
- 规则的动态更新和 A/B 测试能力。
- 分类结果的审计日志和人工复核流程。
- 多语言支持（中文、日文、韩文等的敏感信息模式）。
- 分类准确率监控和规则调优。
- 未来可能需要 LLM 辅助分类的评估框架（但需要解决推理成本、稳定性和安全性问题）。
