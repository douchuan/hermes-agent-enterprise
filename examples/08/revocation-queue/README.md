# 示例：第三方授权撤销重试队列

对应书籍：第 8 章 — 凭证管理与权限最小化

## 目的

演示当员工转岗或离职时，平台如何在撤销内部授权连接后，可靠地完成第三方系统（如 GitHub、Slack）的 Token 撤销。

## 原理

第三方授权撤销是一个**异步后续动作**，不应阻塞员工的转岗/离职流程：

1. 平台侧先阻断：撤销内部连接记录，Tool Gateway 立刻拒绝新的工具调用。
2. 第三方撤销进入持久化队列，异步执行。
3. 采用指数退避 + 随机抖动策略重试。
4. 区分不同 HTTP 错误类型，采取不同策略：
   - `429`：遵守 `Retry-After` 头
   - `5xx / 超时`：继续重试
   - `401/403`：可能已撤销，停止重试，标记成功
   - 不可恢复错误：转人工
5. 最大尝试 10 次或 24 小时截止时间。
6. 队列积压时触发告警。

## 运行方式

```bash
cd examples/08/revocation-queue

```

需要 Node.js 18+。测试不依赖外部服务（使用 mock HTTP 客户端）。

## 预期结果

测试应全部通过，展示：
- 正常撤销流程（成功撤销第三方 Token）
- 429 限流处理（遵守 Retry-After）
- 5xx 错误重试（指数退避）
- 401/403 已撤销场景（停止重试，标记成功）
- 超时和不可恢复错误处理
- 队列持久化（模拟重启后恢复）

## 关键设计

- **不阻塞主流程**：撤销第三方 Token 是异步操作，不影响员工转岗/离职的主流程。
- **持久化队列**：模拟 PostgreSQL-backed 队列，进程重启不丢失任务。
- **智能重试**：根据 HTTP 状态码分类处理，避免无意义重试。
- **审计事件**：每次尝试和最终结果都记录到审计日志。
- **退避 + 抖动**：防止重试风暴，参数在 `types.ts` 中配置。

## 安全边界

- 本示例使用 mock HTTP 客户端，不实际调用第三方 API。
- 重试参数（最大次数、退避倍数、超时时间）是参考值，需要根据供应商 API 调整。
- 示例中的队列是内存模拟，生产环境需要真实的持久化存储。
- 示例未实现队列加密和访问控制。

## 生产差距

生产环境需要补充：

- 真实的持久化队列（PostgreSQL、Redis 或消息队列）。
- 供应商特定的撤销 API 适配层（GitHub、Slack、Google 等各有不同的撤销端点）。
- 队列积压监控和告警（Prometheus 指标）。
- 不可恢复任务的人工处理流程。
- 队列条目的加密存储和访问控制。
- 撤销完成后的审计事件关联（将平台侧阻断和第三方撤销关联到同一 Trace）。
